# 로또청약 알리미 모바일 앱 설계 (v0.2, 2026-11-03)

PC 프로그램(v1.3)의 기능을 안드로이드·iOS 앱으로 옮긴다.
핵심 원칙: **휴대폰은 공공데이터 API를 조회하지 않는다. 서버가 조회하고 푸시로 알린다.**

## 0. 지인 배포 단계 구조: GitHub 서버 (2026-11-03 결정)

아래 1~11장의 Firebase 서버 구조는 사용자가 많아졌을 때의 목표로 두고,
지인 배포 단계는 **GitHub Actions를 서버로, FCM 토픽으로 푸시, 조건 비교는 앱**에서 한다.

```
GitHub Actions (10분마다, 키는 Secrets)
  ├─ notices.json / status.json → gh-pages → GitHub Pages (앱이 목록·상세로 읽음)
  └─ 새 공고 → FCM 데이터 메시지 → 토픽 '{시도}_{유형}' (예: gyeonggi_muns, seoul_happy)
                                     ▼
APK: 내 지역 × 유형 토픽만 구독 → 받은 데이터로 차익·가격·자격을 직접 점검
     → 맞으면 앱이 알림 표시 (채널, 조용한 시간도 앱이 처리) / 앱을 열면 notices.json으로 놓친 공고 보충
```

| 항목 | GitHub 단계 | Firebase 단계 (1~11장) |
|---|---|---|
| 서버 | GitHub Actions (무료, 공개 저장소) | Cloud Run Job (Blaze) |
| 데이터 | GitHub Pages JSON | Firestore |
| 내 조건 | **휴대폰에만 저장** | 서버 users 문서 |
| 매칭 | 지역·유형=토픽, 나머지=앱 | 서버 |
| 조용한 시간·묶음 | 앱 | 서버 |
| 주간 요약 | 앱이 notices.json으로 로컬 예약 | 서버 |
| Firebase | FCM만 (Spark 무료) | FCM·Firestore·Auth |

- 코드: `server/github_run.py`(실행), `server/topics.py`(토픽 이름), `.github/workflows/collect.yml`. 수집·정규화는 Firebase 단계와 같은 `collector.collect_all`, `normalize.py`를 쓴다.
- FCM 메시지 데이터(문자열 값): `v, id, src, cat, title, sido, addr, start, end, maxGap, units(JSON), more`
  - 분양형 units: `[면적, 분양가(만원), 시세(만원), 차익(만원), 일반세대, 특별세대]`
  - 임대형 units: `[호수, 보증금(원), 월임대료(원), 시도, 광역시도명]`
- 앱은 `eligibility.self_check`, `match.prefs_match` 규칙을 Dart로 옮겨 쓴다 (규칙 원본은 Python).
- 앱이 받고도 띄우지 않는 메시지가 많으면 안드로이드가 우선순위를 낮추므로, 토픽을 시도×유형으로 잘게 나눴다.
- 한계: Actions 예약 실행이 몇 분 늦을 수 있음. 공공데이터 API의 해외 IP 허용 여부는 첫 실행으로 확인.

## 1. 목표와 범위

| 구분 | 내용 |
|---|---|
| 1차 목표 | 지인 수십 명 대상 안드로이드 앱(APK) 배포. PC 프로그램과 같은 알림 품질 |
| 2차 목표 | Play 스토어 출시 → iOS 출시. 사용자 수천 명까지 구조 변경 없이 운영 |
| 대상 공고 | 청약홈 무순위·계약취소 재공급(시세·차익·자격 점검 포함), 마이홈 공공임대·공공분양 |
| 이번 범위 밖 | 일반 APT 청약, SH·GH 게시판 수집, 카카오 알림톡, 웹(PWA) |

## 2. 전체 구조

```
                 ┌──────────── Google Cloud / Firebase (한 프로젝트) ────────────┐
 Cloud Scheduler │                                                              │
 (10분마다) ─────┼─> Cloud Run Job  "collector" (Python, 기존 코드 재사용)          │
                 │     1. 청약홈·마이홈 조회 → 새 공고/변경 공고 찾기              │
                 │     2. 공고 보강: 주택형, 시세(국토부 실거래), 공고문 PDF 링크    │
                 │     3. Firestore notices 저장                                │
                 │     4. 사용자 조건과 매칭 → 사용자별 자격 점검 → 푸시 목록      │
                 │     5. FCM 발송 (조용한 시간이면 대기열에 보관)                 │
                 │                                                              │
                 │   Firestore  ← 앱이 직접 읽기/쓰기 (보안 규칙으로 제한)         │
                 │   Secret Manager: 공공데이터 키, 운영자 텔레그램 봇 토큰        │
                 └───────────────────────────┬──────────────────────────────────┘
                                             │ FCM (iOS는 APNs 경유)
                                             ▼
                          앱 (Flutter, 안드로이드 → iOS)
                          - 익명 로그인, 내 조건·알림 설정 저장
                          - 공고 목록·상세, 관심 공고
                          - 관심 공고 일정 알림은 기기에서 로컬 예약
```

**별도 API 서버를 두지 않는다.** 앱은 Firestore를 직접 읽고 쓴다. 공고는 누구나 읽기, 사용자 문서는 본인만 읽기/쓰기로 제한한다. 서버 코드는 10분마다 도는 작업(collector) 하나뿐이다.

### 기술 선택

| 항목 | 선택 | 이유 |
|---|---|---|
| 앱 | **Flutter** (결정 2026-11-03) | 안드로이드·iOS 한 코드. Firebase 공식 플러그인(FCM, Auth, Firestore)과 로컬 알림 플러그인이 안정적. 대안: React Native(Expo) |
| 서버 실행 | Cloud Run Job + Cloud Scheduler | 기존 Python 코드를 컨테이너로 그대로 실행. 10분마다 1~2분 실행이라 무료 범위 |
| DB | Firestore | 앱 직접 연동, 실시간 갱신, 보안 규칙 |
| 로그인 | Firebase 익명 로그인 | 가입 절차 없음. 나중에 Google/Apple 로그인으로 계정 연결 가능 |
| 푸시 | FCM | 무료, 안드로이드·iOS 공통 |
| 운영 알림 | 텔레그램(운영자 1명) | 수집 실패를 운영자만 받음. 기존 코드 재사용 |

## 3. 데이터 모델 (Firestore)

### notices/{noticeId}  — 공고 1건 (서버만 쓰기, 누구나 읽기)
```
id:            "AH_2026000123_1" | "MH_공공임대_21480" | "MH_공공분양_1496"
source:        "applyhome" | "myhome_rent" | "myhome_sale"
category:      "무순위" | "불법행위 재공급" | "행복주택" | "국민임대" | ... (myhome.CATEGORIES)
title, agency (LH 등), status ("일반공고"/"정정공고")
sido:          "경기"            # 짧은 이름 (매칭·필터용)
sidoFull, sigungu, address
dates:         {announce, applyStart, applyEnd, winner}   # "YYYY-MM-DD"
units:         [ { name, area_m2, count_general, count_special,
                   price_manwon, market_manwon, market_basis, market_count, gap_manwon,
                   deposit_won, rent_won } ]               # 분양형은 price/market, 임대형은 deposit/rent
maxGapManwon:  최대 차익 (목록 정렬·필터용)
eligibility:   { summary: [...], requiredResidence: "시도" | "광역" | "전국" | null }
links:         { pdf, applyhome, myhome, lh }
createdAt, updatedAt, closed (접수 종료 여부)
```

### users/{uid}  — 사용자 1명 (본인만 읽기/쓰기)
키 이름은 PC 프로그램 config.json과 같게 맞췄다 (PC 설정을 그대로 서버 시험 사용자로 쓸 수 있음).
```
profile:   { region, address, householder, homeless, special_eligible, abroad_90d, restricted }
           # 값은 true / false / null(모름). PC 프로그램 my_profile과 같음
prefs: {
  regions: ["경기", "서울"],                    # 비우면 전국
  lotto_enabled: true, house_types: ["무순위", "불법행위 재공급"],
  public_housing: { enabled: true, types: ["행복주택"] },   # types 비우면 전체
  min_gap_manwon: 10000, max_price_manwon: null, min_area_m2, max_area_m2,
  include_keywords: [], exclude_keywords: [], notify_if_no_market: true,
  hide_ineligible: true,
  quiet_hours: { enabled: true, start: "22:00", end: "08:00", lotto_bypass: true },
  weekly_digest: true
}
createdAt, updatedAt
```

### users/{uid}/devices/{fcmToken}
```
platform: "android" | "ios", appVersion, locale, updatedAt
```
- FCM이 `UNREGISTERED` 오류를 주면 서버가 해당 토큰 문서를 지운다.

### users/{uid}/watchlist/{noticeId}
```
addedAt   # 관심 등록. 앱이 이 공고의 일정 알림을 기기에 예약
```

### users/{uid}/inbox/{noticeId}  — 이 사용자에게 보낸(보낼) 알림
```
noticeId, grade: "ok" | "warn" | "no", checks: [...],   # 사용자별 자격 점검 결과
sentAt | queuedUntil (조용한 시간이면 발송 예정 시각), read
```
- 중복 발송 방지 키 역할도 한다 (문서가 이미 있으면 다시 보내지 않음).
- 앱의 "내 알림" 탭이 이 컬렉션을 보여 준다.

### outbox/{uid}__{noticeId}  — 조용한 시간이라 대기 중인 알림 (서버 전용)
```
uid, nid, due   # 발송 예정 시각. 발송 후 삭제
```
- 컬렉션 그룹 쿼리 없이 `due <= 지금` 한 번으로 찾기 위해 최상위 컬렉션으로 둔다.

### system/collector, cache/{key}
- `system/collector`: lastRun, lastSuccess, failCount, 소스별 상태 (PC의 meta 테이블 대응)
- `cache/{key}`: 지역코드·실거래 조회 캐시 (PC의 sqlite cache 테이블 대응, TTL 1~7일)

### 보안 규칙 요약
```
notices/*            read: true                      write: false (서버 관리자 키만)
users/{uid}/**       read, write: request.auth.uid == uid
                     단, inbox는 read와 read 표시(update read 필드)만 허용
system/*, cache/*    read, write: false
```

## 4. 서버 (collector) 처리 흐름

```
run():
  state = system/collector
  for source in [applyhome, myhome]:          # 소스별로 실패를 분리 (한쪽 실패가 다른 쪽을 막지 않음)
      raw = fetch(source)
      for notice in raw:
          if new or changed(hash):            # 정정공고·마감 상태 변화 반영
              enrich(notice)                  # 주택형, 시세, PDF 링크 (새 공고당 1번)
              upsert notices/{id}
              if new: queue_match(notice)
  users = load all users (prefs, profile)     # 사용자 수천 명까지 메모리로 충분
  for notice in matched_queue:
      for user in users:
          if prefs_match(user.prefs, notice):
              result = self_check(user.profile, notice)
              if result.grade == "no" and prefs.hideIneligible: continue
              write inbox (sent or queued)
  flush_queued()                              # 조용한 시간이 끝난 대기 알림 발송
  send_push()                                 # 사용자별 묶음 처리 후 FCM
  weekly_digest() if Monday 08:xx
  update state; if failCount >= 3 → 운영자 텔레그램
```

### 기존 코드 재사용 지도

| PC 코드 | 서버 모듈 | 바꿀 점 |
|---|---|---|
| `main.api_get`, `http_json` | `sources/applyhome.py` | 그대로 |
| `myhome.py` (fetch, group, category, region_ok) | `sources/myhome.py` | 그대로 |
| `main.notice_ok`, `model_ok`, `gap_filter` | `match.py` `prefs_match(prefs, notice)` | cfg(dict) 대신 prefs, 공고는 정규화된 notices 문서 기준 |
| `price.PriceLookup` | `enrich/price.py` | sqlite 캐시를 저장소 인터페이스(get/set)로 분리 → Firestore cache |
| `eligibility.summary`, `pdf_link`, `self_check` | `eligibility.py` | 그대로 (입력이 같은 dict 구조가 되도록 정규화 단계에서 맞춤) |
| `build_message` (텔레그램 HTML) | `push.py` | 푸시용 짧은 제목·본문 + 상세는 앱 화면 |
| `daily_report` | `weekly_digest` + 운영자 상태 알림 | 사용자에게 "정상 동작 중"은 보내지 않음 |

**정규화가 핵심이다.** 청약홈과 마이홈 응답을 위의 `notices` 구조 하나로 바꾸는 `normalize()`를 먼저 만들고, 매칭·자격·푸시는 이 구조만 본다. 그래야 나중에 일반 APT, SH 게시판 등 새 소스를 붙일 때 정규화만 추가하면 된다.

### API 호출량 (하루)

| 소스 | 호출 | 하루 |
|---|---|---|
| 청약홈 무순위 목록 | 10분마다 1회 | 144 |
| 청약홈 주택형 | 새 공고당 1회 | 수 건 |
| 마이홈 임대·분양 | 10분마다 2회 | 288 |
| 실거래·지역코드 | 새 공고의 시군구당 6개월, 캐시 | 수십 건 |

사용자 수와 관계없이 일정하다. 마이홈 개발계정 한도(1,000건/일) 안이지만, 출시 전에 **운영계정 전환(활용사례 등록)**을 해 둔다.

## 5. 알림 설계

### 채널 (안드로이드 Notification Channel = iOS 앱 내 설정)

| 채널 ID | 이름 | 중요도 | 내용 |
|---|---|---|---|
| `lotto` | 🎯 로또 청약 | 높음 (소리, 상단 팝업) | 무순위·재공급 중 내 조건 통과 |
| `public` | 🏠 공공주택 | 보통 | 행복주택·국민임대·공공분양 등 |
| `schedule` | 📅 일정 | 보통 | 관심 공고 접수 전날 20시, 당일 9시, 마감일 9시 (기기 로컬 예약) |
| `digest` | ☀️ 주간 요약 | 낮음 (무음) | 월요일 8시 "이번 주 접수 일정 n건" |

### 푸시 내용 예
```
제목: 🎯 [무순위] 동탄역 ○○ 1세대 · 차익 +3.2억
본문: 접수 11/10~11/11 · 분양가 4.1억 · 시세 7.3억 · ✅ 기본 요건 충족
제목: 🏠 [행복주택] 과천지식정보타운 S12 · 1,424호
본문: 접수 11/10~11/12 · 보증금 5,160만원~ · 월 21만원~
```
- 데이터 페이로드에 `noticeId`를 넣어 알림을 누르면 상세 화면으로 바로 이동한다.
- 한 번 실행에서 같은 사용자에게 3건 이상이면 "새 공고 n건" 묶음 알림 1개로 보낸다.

### 조용한 시간
- 기본값은 22:00~08:00. 이 시간에 생긴 알림은 `inbox.queuedUntil`에 넣고, 08:00 이후 첫 실행 때 묶어서 보낸다.
- `lotto` 채널은 기본으로 예외(바로 발송). 사용자가 끌 수 있다. 무순위는 접수 기간이 1~2일로 짧기 때문이다.

### 알림 권한 요청 시점
- 앱 첫 실행 직후가 아니라 **온보딩 마지막 단계("이 조건으로 알림 받기")**에서 요청한다. 이유를 설명한 뒤 요청하면 허용률이 높다.
- 안드로이드 13 이상(POST_NOTIFICATIONS), iOS 모두 거부 시 설정 화면에 "알림이 꺼져 있습니다 → 켜기" 배너를 둔다.

## 6. 앱 화면

```
[온보딩 3단계]  지역·거주지 → 자격 질문(세대주·무주택·특공·제한, 모름 허용) → 알림 종류·차익 기준 → 권한 요청
[홈 탭]        접수 예정·진행 중 공고 목록 (필터: 로또/공공, 지역, 마감 임박순·차익순), 카드에 ✅⚠️❌
[상세]         일정, 주택형별 분양가·시세·차익 또는 보증금·월세, 내 자격 점검, 공고문 PDF·청약홈 링크, [관심 등록]
[내 알림 탭]   inbox 목록 (읽음 표시)
[관심 탭]      관심 공고와 다가오는 일정
[설정 탭]      내 조건, 알림 조건, 채널별 켜기/끄기, 조용한 시간, 개인정보 삭제(계정 삭제)
```
- 온보딩 질문은 [청약자격 조사 문서 7장](청약자격_조사_및_설문설계.md)의 1·2단계 설문을 그대로 쓴다.
- 앱은 Firestore 실시간 구독으로 목록을 갱신한다. 오프라인에서도 마지막 목록을 보여 준다(Firestore 캐시).

## 7. 보안과 개인정보

- **앱에는 공공데이터 키·봇 토큰을 넣지 않는다.** 앱에 들어가는 Firebase 설정값은 공개되어도 되는 값이고, 접근은 보안 규칙으로 막는다. 출시 전 Firebase App Check를 켠다.
- 수집하는 개인정보: 거주 시·도/시·군, 세대주·무주택 등 자격 답변, 기기 토큰. 이름·전화번호·주민번호는 받지 않는다.
- 스토어 출시에는 **개인정보처리방침 URL**이 필요하다. 설정에 "내 정보 삭제" 기능(사용자 문서와 하위 컬렉션 삭제)을 둔다.
- 모든 화면과 알림에 "시세·자격은 참고용 추정, 최종 판단은 모집공고문" 문구를 유지한다.

## 8. 비용 (월, 사용자 1,000명 기준 추정)

| 항목 | 예상 |
|---|---|
| Cloud Run Job (10분마다 1~2분) | 무료 범위 |
| Cloud Scheduler (작업 1개) | 무료 범위 (계정당 3개 무료) |
| Firestore (읽기: 앱 목록 조회가 대부분) | 무료 범위 ~ 수천 원 |
| FCM | 무료 |
| Google Play 개발자 등록 | $25 (1회) |
| Apple Developer Program (iOS 푸시 필수) | $99 / 년 |

Cloud Run·Scheduler를 쓰려면 Firebase **Blaze(종량제) 요금제**로 결제 수단을 등록해야 한다. 무료 범위를 넘지 않으면 청구되지 않으며, 예산 알림(예: 월 5,000원)을 설정해 둔다.

## 9. 단계별 계획과 완료 기준

| 단계 | 작업 | 완료 기준 |
|---|---|---|
| **1. 서버** | 정규화·매칭 모듈 분리, Firestore 저장, Cloud Run Job 배포, 운영자 텔레그램 | PC 프로그램과 같은 공고가 notices에 쌓이고, 테스트 사용자 문서 1개에 대해 inbox가 PC 알림과 같게 생성됨 (2주 병행 비교) |
| **2. 앱 MVP** | Flutter 앱: 익명 로그인, 온보딩, 홈·상세, FCM 수신, 설정 | 안드로이드 APK를 지인 5명에게 설치, 새 공고 푸시가 1분 안에 도착 |
| **3. 알림 고도화** | 관심 공고 로컬 일정 알림, 조용한 시간, 묶음 알림, 주간 요약 | 일정 알림이 정해진 시각에 울림, 밤 알림이 아침에 묶여 도착 |
| **4. 출시** | 개인정보처리방침, App Check, Play 스토어(비공개 테스트 → 공개), iOS | 스토어 심사 통과 |

PC 프로그램과 텔레그램 알림은 2단계가 끝날 때까지 그대로 유지한다.

## 10. 결정이 필요한 것

1. **앱 프레임워크**: Flutter(권장) / React Native(Expo)
2. **Firebase 프로젝트 생성과 Blaze 요금제 결제 수단 등록** (사용자가 직접 진행)
3. **앱 이름과 패키지 ID** (예: `kr.lottocheongyak.app`, 출시 후 변경 불가)
4. **운영 범위**: 지인 배포까지만 할지, 스토어 공개까지 할지 (개인정보처리방침·운영계정 필요 여부가 달라짐)
